# Severity, concerns and actions
Use the helper's rules command. It validates the pack and matches exact control/evidence-status predicates. Model judgement selects evidence status; executable code enforces the approved mapping. This does not make evidence interpretation deterministic.
Severity: Critical, High, Medium, Low; Unassigned when a required rule is missing or ambiguous. None is allowed only for a result with no concern under an explicit rule. Unassigned is never treated as Low. A triggered hard gate requires a concern and explicit human review. No model decision authorises proceeding. Missing evidence alone is not failure unless the rule says so. Never offset a concern with another control's evidence.
Create a concern when the rule returns a severity or hard gate. For an unresolved Unassigned result, create a provisional concern and a blocking question. Record concern ID, control ID, rule ID, finding, rationale, severity, hard gate, evidence references, evidence gap, state, action, proposed owner, due date, closure evidence required and history. Assign new IDs uniquely within the project package. Preserve old IDs only with validated continuity. Deduplicate only where control, evidence and finding genuinely describe the same issue; never merge uncertain records silently.
Actions must describe a concrete artefact or change, why it addresses the control, verification evidence and a proposed accountable function. Mark proposed owners as proposals and unknown names/dates TBC. Severity ordering can prioritise the plan but is not a new policy rule. Do not invent deadlines, risk appetite or an assurance outcome. Keep next steps and specialist-review requests linked to concerns and questions.
